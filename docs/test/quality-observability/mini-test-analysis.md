# mini テスト分析: quality-observability

> 詳細は本編 [`test-analysis.md`](test-analysis.md) を参照。本書は nput の CI・品質基盤に
> 詳しくない人向けの要約。リスク番号（①〜⑥）は [`mini-test-plan.md`](mini-test-plan.md) と共通。

## 1 分で分かるテスト分析

テスト計画（[`mini-test-plan.md`](mini-test-plan.md)）で「何が怖いか」を洗い出した。
この分析はその次の工程で、**「では具体的に何を確認すればよいか」を 14 個の観点に整理した**もの。
まだ「どんな値を入れて何が返るか」は決めない（それは次工程のテスト設計）。

対象は、nput が外に約束している機能 17 個（CLI コマンド 6・Nix ライブラリ関数 6・モジュール
設定項目 5）の対応表（台帳）を自動生成し、その腐敗を CI が検出してマージを止める仕組み。

## 何を確認するか

優先度の高い順。かっこ内は本編の観点番号。

| 一言でいうと | なぜ必要か | 本編 |
|---|---|---|
| 台帳だけ直した PR でも検証が走り、逆に重い nix テストは走らないこと | 走らなければ壊れた台帳が素通りする（①）。逆に走りすぎれば時間とコストの無駄（③） | TC-01 |
| 壊れた台帳の PR は、CI が赤くなるだけでなく**マージも実際にできない**こと | 赤くなるだけでは「マージ必須チェック」への登録漏れを見逃す（①） | TC-02 |
| 何度生成しても結果が同じこと | 毎回変われば正しい PR まで赤くなり、仕組みごと信用を失う（②） | TC-03 |
| 機能 17 個の数え方が仕様の規則どおりであること | 間違えやすい箇所が 3 つある（数えてはいけない取り込み行・除外すべき設定・入れ子の項目）（④） | TC-04 |
| 台帳が 17 個を過不足なく載せ、該当が無い欄は「なし」と書かれること | 空欄と「なし」を区別しないと、記述漏れなのか未確認なのか分からない（④⑤） | TC-05 |
| 台帳の表の形が仕様どおりであること（列の構成・余計な列が無い） | 形が違っても「生成物と一致」の検査は通ってしまい、恒久的に誤ったまま緑になる | TC-06 |
| 壊れた台帳を 4 通りの壊し方すべてで検出し、理由を出すこと | 検出できなければ CI が正しく走っても意味がない | TC-07 |
| 検証しても台帳を書き換えないこと | 検証が勝手に直すと、壊れていた事実が消えて人に伝わらない | TC-08 |
| ツールが `nix run` で起動すること（生成・検証の両方） | 現状どちらの flake にも起動口が無く、全面的に新規追加のため | TC-09 |
| テスト一覧に 4 種類すべてが名前・場所・種別つきで出ること | 一部（namaka スナップショット）が静かに漏れやすい（⑥） | TC-10 |
| 生成が Nix 評価なしで完結すること | 評価に頼ると遅く・環境依存になる。仕様が明示的に禁じている | TC-11 |
| 検証成功時は何も出力しないこと | 既存の設計方針「成功時は沈黙」に従う | TC-12 |
| 開発用ツールが利用者向けの公開面に漏れ出ないこと | 配布物にも CLI にも開発専用ツールを混ぜない | TC-13 |
| ドキュメント 3 箇所が追従していること | 完成の定義・設計書・台帳の README。特に README には「対応があること以上は保証しない」という限界を書く必要がある | TC-14 |

## 何が怖いか

- **①③ CI 配線のミス**（最重点）— 台帳だけの PR で検証がスキップされると、CI 上は
  「成功」扱いになるため誰も気づかない。逆方向のミス（重い nix テストが無駄に走る）も同じ配線が原因。
- **② 生成結果のぶれ** — 揺れると全 PR が赤くなり、仕組みごと無効化される。回復コストが高い。
- **④ 数え方のずれ・⑤ 仕様参照の「なし」多発** — ⑤ は記述不足を可視化した正しい結果なので、
  「なし」が多いこと自体は問題視しない。
- **⑥ 一部テストの漏れ** — 影響は限定的。

## やらないこと

- **テストが機能を本当に検証しているかの判定** — 台帳が保証するのは「対応関係がある」ことまで
  （仕様が明示する限界）。ただし**その限界を README に書くこと自体は確認する**（TC-14）
- **テスト一覧の鮮度チェック** — 一覧は俯瞰用の参考資料で、マージ判定に使わないため
- **既存テスト（Go 254 件・nix-unit 58 件など）自体の再検証** — 今回触らない既実装
- **性能・セキュリティ** — 開発者専用の内部ツールで、規模も小さいため

## 補足: この分析で気をつけた点

受け入れ条件（仕様書の「これが満たされれば OK」リスト）は 19 件あるが、**それを全部満たしても
実装漏れが残る要求が 2 つある**（台帳の表の形と、README への限界明記）。どちらも対応する
受け入れ条件を持たないため、受け入れ条件の網羅だけを完了判定に使うと見落とす。
本編ではこの 2 つを TC-06・TC-14 として独立に条件化している。
