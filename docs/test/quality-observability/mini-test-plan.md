# mini テスト計画: quality-observability

> 詳細は本編 [`test-plan.md`](test-plan.md) を参照。本書は nput の CI・品質基盤に詳しくない人向けの要約。

## 1 分で分かる quality-observability

nput には「外に約束している機能」（CLI コマンド 6 個・Nix ライブラリ関数 6 個・モジュール
設定項目 5 個 = 計 17 個）がある。それぞれについて「仕様書のどこに書いてあるか」「テストが
どこにあるか」を 1 枚の対応表（台帳）に自動生成し、対応の欠落や表の古さを CI が検出して
main へのマージを止める仕組みを作る。今回テストするのは、この**台帳の生成・検証ツールと、
マージを止める CI の配線**が正しく働くかどうか。

## 何が怖いか（リスク）

| # | 一言でいうと | 怖さ |
|---|---|---|
| ① | 台帳だけ直した PR で検証がスキップされ、壊れた台帳がそのまま main に入る（スキップは CI 上「成功」扱いなので誰も気づかない） | 高 |
| ② | 生成結果が実行のたびに微妙に変わり、正しい PR まで全部エラーになって仕組みごと信用を失う | 高 |
| ③ | CI 配線のミスで、ドキュメントしか触っていない PR なのに重い nix テストが全部走る（コストと時間の無駄） | 中 |
| ④ | 「機能 17 個」の数え方が実装と表でずれて、件数が合わなくなる | 中 |
| ⑤ | 仕様書に見出しの ID が無いため、台帳の「仕様参照」欄の大半が「なし」になる（ただしこれは記述不足の可視化という本来の目的どおりの結果） | 中 |
| ⑥ | 一部のテスト（namaka スナップショット）が一覧から漏れる | 低 |

## 何をどこまでテストするか

- **CI が本当にマージを止めるか**（①③）を最重点にする。変更内容の異なる 4 種類の PR を
  実際に作り、「検証が走るべき PR で走る / 走らなくてよい PR で走らない」を確認するのに
  加えて、**壊した台帳の PR で check が赤くなり、かつマージがブロックされる**ことまで
  確認する（赤くなるだけでは、マージ必須チェックへの登録漏れを見逃すため）。
- **生成結果が毎回同じか**（②）を厚くする。単に 2 回実行して比べるだけでなく、ファイルの
  読み込み順を変えても同じ結果になることまで見る。
- 数え方の境界（④）は、間違えやすい 3 箇所（数えてはいけない取り込み行・除外すべき
  flake-parts の設定・入れ子の設定項目）を個別に確認する。
- ツールの基本動作（壊した台帳を 4 通りの方法で検出できるか・実行しても台帳を書き換えないか
  など）は標準的な厚さで確認する。

## いつ終わりか（完了基準）

- 高リスク（①②）に対応するテストが全部実行され、全部合格している
- 仕様の受け入れ条件 19 件すべてに対応するテストがあり、合格している
- 4 種類の PR パターンすべてで CI の動きが期待どおりだったことが確認済み
- 「壊した台帳の PR はマージできない」ことが実際の PR で確認済み
- 重大な欠陥（腐敗を見逃す・正しい PR を誤って落とす）が 0 件

## やらないこと

- **テストが機能を本当に検証しているかの判定** — 台帳が保証するのは「対応関係がある」こと
  まで。中身の良し悪しは見ない（仕様が明示する限界）
- **カバレッジの閾値でマージを止めること** — 既存の設計判断（マージ順で結果が変わる問題を
  避ける）を維持
- **テスト一覧の鮮度の自動チェック** — 一覧は全体を俯瞰するための参考資料で、台帳と違い
  マージ判定には使わないため
- **仕様書への ID 付与** — 別の作業として台帳の出力を見てから決める
