## 1. 採用テスト技法と選定根拠

利用者承認済みの方針: **デシジョンテーブル + 同値分割/境界値分析 + エラー推測** の 3 本立てを
中核に置き、静的な存在確認で足りる条件はチェックリストで導出する。カバレッジ基準は
**全ルール網羅・全同値クラス網羅**（構造ベースのブランチカバレッジは対象未実装のため課さない。
→ 2 章）。ケース数の上限は設けない。

| 対応テスト条件 | 採用技法 | 選定根拠（対象の特性）| カバレッジ基準 |
|---|---|---|---|
| TC-01 | デシジョンテーブル | PR の変更内容（条件）とゲート方式の異なる 3 つの観測対象（動作）の組合せで期待が変わる。test-plan 3 章 (a) が変更パターン ①〜④ を固定済みで、条件が離散・有限のためルール表へそのまま落ちる | 全ルール（4 パターン × 観測対象 3 系統 = 12 判定点） |
| TC-02 | デシジョンテーブル | 台帳の状態（健全 / 腐敗）と 2 つの判定点（check が failure として報告されるか / required status check によりマージが不可能になるか）の組合せで期待が変わる。腐敗時に①だけ成立（check は赤いがマージできる = ruleset 登録漏れ）を検出するには判定点を分けて扱う必要があり、健全時は逆に**両方とも不成立**（success かつマージ可能）でなければ偽陽性になる | 全ルール（健全 2 判定点 + 腐敗 2 判定点） |
| TC-03 | エラー推測 | 決定論性の破れは仕様に書かれた条件ではなく、実装がソートを欠く箇所（glob の列挙順・連想配列の反復順）や環境依存の値を出力へ混ぜる箇所に由来する。仕様ベース技法では導けない「壊れ方の想定」からケースを起こす。R4 が高リスクのため AC-18 の 2 回実行一致に撹乱条件を足す | 想定した非決定性要因（ファイル列挙順・連想配列の反復順・実行環境差）ごとに 1 ケース |
| TC-04 | 同値分割 + 境界値分析 | REQ-02 が数え方の規則を「宣言か取り込み行か」「submodule の親か葉か」「transposed か否か」の離散区分で定めている。各区分が有効/無効同値クラスを形成し、`inherit (lib) mkOption` と transposed オプションは誤計上しやすい境界に当たる | 全同値クラス（有効・無効の各区分）+ 各境界の内外 |
| TC-05 | 同値分割 | 「仕様参照」「テスト所在」列の値が「解決できた（参照を書く）」「解決できない（`なし` を書く）」の 2 クラスに分かれ、クラスごとに期待表現が異なる。AC-05 の `rollback` は後者の代表値 | 両クラス（解決可・解決不可）× 2 列 |
| TC-06 | チェックリスト | 表構造（列の構成・禁止列の不在・「機能」列の内容）は組合せでも値域でもなく、REQ-01 が列挙した規定への適合を 1 件ずつ確認する静的判定。技法を当てても導出結果が規定の逐条確認と一致する | REQ-01 の表構造に関する規定の全項目 |
| TC-07 | デシジョンテーブル | 台帳の壊し方が 5 つの独立した条件（「テスト所在」を実在しないパスへ書き換え / 「仕様参照」を実在しない見出しへ書き換え / 行の削除 / 母集団に無い行の追加 / 内容の手書き換え）で、それぞれ「非ゼロ終了」と「標準エラー出力の内容」の 2 動作を持つ。**REQ-05 は失敗契機を 2 つ持つ**（テスト所在のパス不在・仕様参照の見出し不在）ため独立ルールとして分ける。加えて REQ-05 は `なし` の欄を検証対象外とする**除外規定**を持ち、これは「壊れていないのに失敗させない」ことを見る負例のルールになる | 全ルール（失敗 5 パターン × 判定点 2 件 + 除外規定の負例 1 件 = 11 判定点） |
| TC-08 | 状態遷移（縮退） | 検証モードの実行を「台帳ファイルの状態を変えない遷移」として確認する。実行前後の内容一致が判定点で、成功時・失敗時の双方で非破壊であることを見る | 検証の成功時・失敗時の 2 状態からの遷移 |
| TC-09 | ユースケース | `nix run '.?dir=dev#qa-tracer'` という起動経路そのものが対象で、利用者の操作シナリオ（生成モードで起動する / 検証モードで起動する）に沿って確認する | 生成モード・検証モードの 2 シナリオ |
| TC-10 | 同値分割 | テスト一覧の母集団が種別 4 値（Go / nix-unit / namaka / e2e）の同値クラスに分かれ、各クラスから代表が出ることと必須項目 3 つが揃うことを見る。R6 は namaka クラスの脱落リスク | 全同値クラス（種別 4 値）+ 必須項目 3 つ |
| TC-11 | チェックリスト | 「`nix eval` を呼ばずに完了する」という否定的性質の静的確認。入力の区分も組合せも持たない | AC-04 の判定点 1 件 |
| TC-12 | チェックリスト | 標準出力が空であることの単純アサート。test-plan 3 章が「1 件で足りる」と判断済み | AC-17 の判定点 1 件 |
| TC-13 | チェックリスト | root `flake.nix` の `apps` 出力の不在・`nput --help` へのサブコマンド非出現・`lib/` の依存不変の 3 点を個別に静的確認する。**本条件は AC-13（flake outputs / CLI）と NFR-05（`lib/` の依存）の 2 系統を束ねている**ため、`lib/` の依存を見るケースだけ対応 AC を持たない | 非汚染の判定点 3 件（flake outputs / CLI / lib 依存） |
| TC-14 | チェックリスト | ドキュメント追従（DOD-05 の行の存在と合計件数・設計書の言及・限界の明記）は文字列一致による存在確認。test-plan 3 章が判定手段を「文字列一致の静的確認」と確定済み | 追従先 3 箇所（`definition-of-done.md` / `docs/design.md` / `docs/quality/README.md`）+ 件数上限 1 件 |

### 技法を当てなかった条件について

TC-06・TC-11・TC-12・TC-13・TC-14 にはブラックボックス技法を当てず、チェックリストで導出した。
これらは入力の値域も条件の組合せも持たない**存在確認**で、同値分割や境界値分析を形式的に
適用してもクラスが 1 つしか立たず、規定の逐条確認と同じケースへ帰着するため。技法名の体裁を
整えるより、REQ-01 / AC-04 / AC-13 / AC-16 / AC-19 の規定を漏れなく判定点へ落とすことを優先した。

## 2. カバレッジの確認

### 技法ごとのカバレッジ基準の充足

- **デシジョンテーブル（TC-01）**: 変更パターン ①〜④ × 観測対象（新設の検証 check /
  `e2e`・`go-coverage` / `flake-check` の `Run nix flake check` ステップ）3 系統 = 12 判定点を
  すべてケース化した。観測粒度は test-plan 3 章 (a) の表に従い、`flake-check` は **job の実行
  有無ではなくステップの skip 有無**で判定する（job と matrix は常時起動するため）。
- **デシジョンテーブル（TC-02）**: 台帳の状態（健全 / 腐敗）× 「check の報告状態」
  「マージ可否」の 2 判定点 = 4 判定点。腐敗側は ruleset 登録漏れ（check は failure だが
  マージできる）を検出するため両者を独立したケースへ分け、**健全側は偽陽性
  （常に failure を返す check・正常な PR を止める ruleset）を検出するために置く**。
  健全側が無いと「常に failure を返す実装」がケース全件を通過し、test-plan 完了基準 8 が
  重大欠陥として名指しする「偽陽性で正常な PR が赤になる」状態を検出できない。
- **デシジョンテーブル（TC-07）**: REQ-05（テスト所在のパス不在・仕様参照の見出し不在の
  2 方向）/ REQ-06（不足・過剰の 2 方向）/ REQ-07 の**失敗 5 パターン** ×
  「非ゼロ終了」「標準エラー出力の内容」の 2 動作 = 10 判定点に、**除外規定の負例 1 件
  （CASE-45）を加えた 11 判定点**。REQ-05 は仕様が失敗契機を 2 つ規定しており、
  **「仕様参照」列の見出し実在検証は test-plan 1 章が `docs/spec.md` を
  スコープに含めた根拠（見出しの改名で検証が壊れる）そのもの**のため、独立ルールとして扱う。
  REQ-06 も不足（AC-08）と過剰（AC-09）で条件が異なるため分ける。
  **負例を基準に含めるのは、REQ-05 の「`なし` と記載された欄は検証対象外とし、失敗させない」が
  失敗パターンと対をなす規定であり、これを外すと「何でも失敗させる検証」が失敗系ケースの
  全件を通過するため**。失敗系だけを数える基準では、この過剰検出を検出できない。
- **同値分割 + 境界値（TC-04）**: REQ-02 の 3 系統について、有効クラス（宣言・submodule の
  親と葉・root コマンド以外のサブコマンド・`__internal` 以外の属性）と無効クラス
  （`inherit (lib) mkOption` の取り込み行・transposed オプション・`Use: "nput"` の root
  コマンド・`__internal`）をすべてケース化した。境界の内外は「素朴な走査では 7 ヒットするが
  規則適用後は 5 件」という modules 系統の実測（test-plan R3）を判定点に使う。
- **同値分割（TC-05・TC-10）**: TC-05 は「解決可 / 解決不可」の 2 クラス × 「仕様参照」
  「テスト所在」の 2 列。TC-10 は種別 4 値のすべてから代表が出ることを確認する。
  なお TC-05 のリスク射程は列で異なる（「仕様参照」列のみ R5 に対応し、「テスト所在」列の
  `なし` は REQ-03 の命名規約由来で R5 の射程外。→ `test-analysis.md` 4 章）。
- **エラー推測（TC-03）**: 想定した非決定性の要因 3 つ（ファイル列挙順・連想配列の反復順・
  実行環境差）のそれぞれにケースを立てた。単純な 2 連続実行（AC-18）は偶然一致しうるため、
  それだけでは NFR-03 の保証にならないという test-plan 3 章の判断を引き継ぐ。実行環境差を
  要因に含めるのは、ロケール・タイムゾーン・作業ツリーの絶対パスといった環境由来の値が
  出力へ混入すると、CI の 3 プラットフォーム（`ubuntu-latest` / `ubuntu-24.04-arm` /
  `macos-latest`）間で出力が揺れて REQ-07 の差分検証が恒常的に失敗しうるため。

### 意図的に省いた組合せ

- **構造ベース（ステートメント / ブランチ）カバレッジは設計時点で課さない**。`qa-tracer` は
  未実装で実装言語も未確定（test-plan 開始基準 4）のため、分岐の所在を特定できない。実装後の
  カバレッジ目標を設けるかは test-implement 以降の判断に委ねる。
- **TC-01 の変更パターン間の組合せ爆発は発生しない**。パターンは test-plan が ①〜④ に固定済みで、
  それ以上の細分（例: `docs/spec.md` のみ変更・`**.go` のみ変更）は `quality` フィルタの
  検出対象内か外かで ① または ④ と同じクラスに落ちるため、代表値 1 つに畳んでいる。
- **性能・セキュリティ・ユーザビリティのケースは作らない**（test-plan 3 章・test-analysis
  4 章の判断を踏襲）。
- **既存テスト（Go 254 件 / nix-unit 58 件 / namaka / e2e 7 シナリオ）自体の再検証はしない**。
  TC-10 が確認するのは一覧への出現であって、テストの内容ではない。
- **件数を固定値で比較するケースは作らない**。AC-01 / AC-06 の件数は仕様の「件数表記の扱い」
  節のとおり作成時点のスナップショットで、公開契約・テストの増加に伴って正常に変動する。
  判定は母集団と抽出結果（TC-04・CASE-21・CASE-23）／母集団と台帳（TC-05・CASE-28）／
  実際のテストとテスト一覧（TC-10・CASE-52）の一致で行い、件数はその結果として一致する。
  CASE-27（modules の抽出）も件数の突合ではなく、**素朴な走査と規則適用後の結果が一致しない**
  ことを判定点にしている。

### テスト条件のカバレッジ

TC-01〜TC-14 の 14 条件すべてに 1 件以上のケースが対応している（対応関係は `test-case.md` の
「対応テスト条件」列が正本）。受け入れ条件 AC-01〜AC-19 の 19 件も同様にいずれかのケースへ
対応する。

## 3. 自動/手動の区分基準

`test-case.md` の各ケースに付けた区分（自動/手動）の判定根拠。

### 判定に用いた実行手段（調査結果）

| 実行手段 | 実行方法（コマンド・CI）| 区分 |
|---|---|---|
| Go テスト | `nix build .#nput` の checkPhase 経由。`go-coverage` job が CI で実行 | 自動 |
| nix-unit 評価テスト | `tests/nix-unit/*.nix` へファイルを置くだけで `tests/nix-unit.nix` が自動集約。`nix flake check` に載る | 自動 |
| namaka スナップショット | root `flake.nix` の `checks.namaka`。`nix flake check` に載る | 自動 |
| e2e シェルハーネス | `nix develop '.?dir=dev#ci' -c tests/e2e/run.sh`。`tests/e2e/scenarios/*.sh` を置くと自動で拾われる。`e2e` job が CI で実行 | 自動 |
| 素の bash スクリプト（Nix 非依存）| `tests/traceability/run.sh` が前例。`.github/workflows/test.yml` の job から直接起動 | 自動 |
| 実 PR 上の workflow 実行結果の観測 | GitHub Actions 上で PR を起こし、job / step の実行・skip を確認する | 手動 |
| ruleset のマージ可否の確認 | `main branch protection` ruleset への required status check 登録と、実 PR でのマージ試行 | 手動 |

### 区分の判定基準

- **自動**: 上記の自動区分の実行手段のいずれかで機械実行でき、CI から起動できるもの。
  台帳・テスト一覧の内容検証、検証モードの終了コード・出力の検証、静的な存在確認は
  すべてここに入る。台帳を壊すフィクスチャの作成はスクリプト内で完結するため自動のまま。
- **手動**: 実行に人の操作か管理権限が要るもの、または期待結果が意味判断を含むもの。
  本設計では次の 3 系統に限られる:
  - **実 PR でしか観測できないもの**（TC-01・TC-02）。変更検出の挙動はローカル再現と
    乖離するため、実 PR 上での job / step の実行・skip をもって判定する（test-plan 5 章）。
  - **ruleset の設定に依存するもの**（TC-02 のマージ可否）。required status check の登録には
    リポジトリ管理権限を要し、反映確認はマージ試行まで含む。
  - **期待結果が意味判断を含むもの**（CASE-62）。`docs/quality/README.md` の「読み方と目的が
    対象に詳しくない読み手へ伝わるか」は文字列一致では判定できない。同じファイルでも
    **存在と限界を示す記述の有無は機械判定できる**ため、CASE-61（自動）と CASE-62（手動）へ
    分割している。

### 実装言語の未確定が区分に与える影響

`qa-tracer` の実装言語は基本設計で確定する（test-plan 開始基準 4・R8）。**どの言語を選んでも
自動区分の実行手段が 1 つ以上存在する**ため（Go なら Go テスト、shell / jq なら e2e ハーネスと
同型のシェルテスト、いずれでもない場合も `tests/traceability/run.sh` と同じ素の bash job）、
区分の判定は言語決定を待たずに確定できる。**ケースの区分値にはランナー種別を書かない**
（設計時点では「機械実行可能か否か」だけを確定させ、どのランナーへ載せるかは test-implement が
決める）。

- `dev/flake.nix` の `devShells.default` は Go / gopls を持つが jq・python を持たず、
  `devShells.ci` は jq を持つが Go を持たない。実装言語によっては CI シェルへのツール追加が
  要る（test-plan 5 章）が、これは実行手段の有無ではなく準備の問題であり、区分を変えない。

### 補足

- データ準備等に人手が要る半自動的な検証手段は本設計では発生しない。台帳の破壊・新規
  サブコマンドファイルの追加といったフィクスチャ操作はいずれもスクリプトで再現できる。
- 区分は設計時点の判定。実装時の食い違いは test-implement が `test-case.md` を更新して正とする。

## 4. 改善提案

1. **検証モードの引数形式が仕様から確定できない**。REQ-08 は「生成モードと検証モードを持ち、
   引数で切り替える」と書くのみで、具体的な引数（`--check` / `verify` / `--verify` 等）が
   未定。TC-09 のケースは「生成モード・検証モードのそれぞれで起動できること」を期待結果と
   したが、**test-implement で手順へ具体化する時点では引数の確定が要る**。仕様書ではなく
   基本設計の領分のため、仕様書へは反映せず基本設計での決定を待つ（利用者確認済み）。

## 5. 次のステップ

- `/test-implement quality-observability` を実行し、テストケースをコード or 手順書へ
  具体化する。特に TC-01・TC-02 の手動ケースは実 PR での観測手順として、それ以外の自動ケースは
  実装言語の決定後にランナーを選んで具体化する。
