# テストモニタリング定義: quality-observability

- 対象: 公開契約の台帳生成・検証基盤（`apps.qa-tracer` / `docs/quality/` / CI 検証 check）の
  テストプロセスそのもの。計測対象はテスト工程の成果物であり、台帳の中身ではない
- 作成日: 2026-07-26
- 入力: `docs/test/quality-observability/test-plan.md`（完了基準の紐づけ先）/
  `docs/test/quality-observability/test-analysis.md`（テスト条件 TC-01〜TC-14）/
  `docs/dev/quality-observability/spec.md`（REQ-01〜REQ-10・NFR-01〜NFR-05・AC-01〜AC-19）
- CI/ツール構成（調査結果）:
  - CI プロバイダ: GitHub Actions のみ（`.github/workflows/test.yml` に `changes` /
    `flake-check` / `go-coverage` / `e2e`）
  - テストランナー: Go テスト（`nix build .#nput` の checkPhase 経由。coverprofile と
    func レポートを成果物 `$out` に同梱）/ nix-unit / namaka スナップショット /
    e2e シェルハーネス（`tests/e2e/run.sh`）
  - **JUnit XML 形式の結果出力は存在しない**（Go テストは coverprofile のみ、
    nix-unit / namaka / e2e はランナー生の出力）
  - 既存の可視化: `go-coverage` job が Job Summary へカバレッジ func レポートを出す。
    README バッジ・PR コメント・外部ダッシュボード連携はいずれも無い

## 1. 目的

- テスト工程の成果物間の**対応関係の欠落**（仕様項目・リスクがテスト条件へ引き継がれていない、
  テスト条件がケース化されていない）を CI 上で可視化する。test-plan の完了基準 1・2 は
  「高リスク項目の消化率 100%」「AC-01〜AC-19 の全件に対応するテストが存在」を要求するが、
  そもそも上流 ID が下流成果物へ引き継がれていなければ、消化率の分母自体が欠落する。
  本基盤はその分母の健全性を測る。
- ※ このドキュメントは **計測基盤の定義** であり、集めた数値の分析・傾向判断は範囲外
  （評価は test-report が担当）。

### 計測範囲の限定（重要）

テスト対象（`apps.qa-tracer` / `docs/quality/` / 検証 check）は**本ドキュメント作成時点で
未実装**であり、test-plan の開始基準（`dev/flake.nix` に `apps.qa-tracer` が定義され両モードが
起動する）も未達。`test-case.md` / `test-execution-log.md` も未作成。したがって:

- **今回実装するのはトレーサビリティ系メトリクスのみ**（入力が既に存在し、今すぐ計測できる）。
- 実行系メトリクス（ケース消化率・失敗率・flaky 率・CI ゲート観測・欠陥候補件数）は
  3 章に**定義と取得元・有効化条件を記すが、実装しない**。有効化は取得元の成果物が
  揃ってから行う。

## 2. メトリクス定義（実装済み）

いずれも `tests/traceability/run.sh` が算出し、GitHub Actions の Job Summary へ出力する。
**しきい値ゲートは持たない**（既存 `go-coverage` と同じ方針。→ 4 章）。「しきい値」列は
評価時の目標値であり、未達でも CI は赤くならない。

| メトリクス | 定義 | 取得元 | しきい値 | 対応する完了基準 |
|---|---|---|---|---|
| REQ → テスト条件カバー率 | `spec.md` の機能要求見出し（`### REQ-##`）のうち、`test-analysis.md` から参照されている割合 | `spec.md` の REQ 見出し / `test-analysis.md` 全文 | 100% | 基準 2 の前提（AC の上流にある要求の網羅） |
| NFR → テスト条件カバー率 | `spec.md` の非機能要求（`- **NFR-##**`）のうち、`test-analysis.md` から参照されている割合 | 同上 | 100% | 基準 7（NFR-01 の沈黙）・基準 1（NFR-03 の決定論性は R4 経由で高リスク項目に含まれる）の前提。残る NFR-02・NFR-04・NFR-05 は AC-04・AC-19・AC-13 経由で基準 2 に繋がる |
| AC → テスト条件カバー率 | 受け入れ条件表の AC-## のうち、`test-analysis.md` から参照されている割合 | `spec.md` 受け入れ条件表の第 1 列 / `test-analysis.md` 全文 | 100% | **基準 2**（AC-01〜AC-19 の 19 件すべてに対応するテストが存在すること）の前段 |
| リスク R# → テスト条件カバー率 | `test-plan.md` のプロダクトリスク表の R# のうち、`test-analysis.md` から参照されている割合 | `test-plan.md` リスク評価表の第 1 列 / `test-analysis.md` 全文 | 100%（自主目標。→ 表直後の注記） | **基準 1**（高リスク項目 R1・R4 に対応するテストの消化率 100%）の前提。リスクがテスト条件化されていなければ分母が存在しない |
| テスト条件 TC# → ケース化率 | `test-analysis.md` のテスト条件 TC-## のうち、`test-case.md` から参照されている割合 | `test-analysis.md` テスト観点一覧の第 1 列 / `test-case.md` 全文 | 100% | 基準 1・2 の分母の健全性。ケース化されていない条件は消化率に現れない欠落になる |
| AC → ケース化率 | 受け入れ条件表の AC-## のうち、`test-case.md` から参照されている割合 | `spec.md` 受け入れ条件表の第 1 列 / `test-case.md` 全文 | 100% | **基準 2** の直接の裏付け |

- **リスク R# カバー率のしきい値 100% は自主目標**で、対応する基準 1 から直接は導けない。
  基準 1 が要求するのは高リスク項目（R1・R4）の消化率 100% であり、低リスクの R7・R8 まで
  テスト条件化することは求めていない。それでも全リスクに 100% を課すのは、**リスクを識別
  しながらテスト条件へ引き継がないことを許すと、リスク評価が形骸化する**ため。低リスクゆえに
  条件化しない判断をした場合は、`test-analysis.md` 側にその旨を書けば参照として計上される。
- 同様に **NFR カバー率の 100% も 5 件すべてを対象とする自主目標**で、対応欄に挙げた基準 7・
  基準 1 が直接要求するのは NFR-01・NFR-03 の 2 件に留まる。

### ID 表記の規約（計測の前提）

集計は ID の文字列突き合わせで行うため、**下流成果物の対応 ID 列では範囲表記を使わず個別に
列挙する**（`AC-07〜AC-10` ではなく `AC-07・AC-08・AC-09・AC-10`）。本文中の説明での範囲表記は
許容する。この規約は `test-analysis.md` 2 章の注記に記載済みで、後続の `test-case.md` にも
同様に適用する。

集計器側で範囲を展開する方式は採らない。表記揺れ（`〜` / `~` / `-`）ごとに実装が増えるうえ、
`REQ-05〜REQ-07` のように別 ID 種の範囲も混在するため、範囲が全件を意図したものかを機械が
判別できず、カバー率が実態より高く出る危険がある。

**規約が守られなかった場合、カバー率は実態より高く出る**（低く出るのではない）。参照判定は
ID の前後を非 ID 文字で挟んだ一致で行うため、`AC-07〜AC-10` という範囲表記からは**両端の
AC-07 と AC-10 が「参照あり」と判定され、中間の AC-08・AC-09 だけが未カバーとして現れる**。
つまり範囲表記は欠落を全部隠すのではなく部分的に隠し、しかも隠れる側が偽陽性になる。
この端点マッチによる偽陽性は集計器では検出できないため、規約の遵守が前提になる。

### 上流の ID 省略記法（スラッシュ併記の限界）

仕様書の受け入れ条件表は、1 つの条件が複数の要求にまたがるとき対象列へ `REQ-02/03` の
ように併記する（feature-spec のテンプレートが認める記法で、本仕様書でも AC-04・AC-17 が
使っている）。この記法は **2 件目以降の ID を省略した形**であり、`REQ-03` という文字列は
どこにも現れない。

参照判定は文字列一致で行うため、**下流成果物がこの記法をそのまま引き写すと、2 件目以降は
「参照なし」と判定される**。範囲表記が偽陽性（実態より高く出る）を生むのとは逆で、
**こちらは偽陰性（実態より低く出る）になる**。

集計器側で展開する方式は採らない。範囲表記を展開しない判断（前節）と一貫させるためで、
`REQ-05/06/07（NFR-01）` のように別 ID 種が混じる形もあり、機械的な復元は表記への依存を
増やす。**下流成果物では省略せず `REQ-02・REQ-03` と個別に列挙する**ことで回避できるため、
規約（前節）の適用範囲としてはこの記法も含む。

なお仕様書側の表記を変える必要はない。上流は母数の抽出元で、抽出は表の第 1 列（`AC-##`）
から行うため対象列の記法に影響されない。問題になるのは下流が引き写した場合だけ。

### 参照判定の範囲（全文突合の限界）

参照の有無は**下流成果物の全文**に対して判定する（表の対応 ID 列だけに絞っていない）。
このため、スコープ節や優先度の根拠といった散文で ID に触れただけでも「引き継がれた」と
計上される。ID 表記の規約が対応 ID 列を前提に書かれているのに対し、計測の適用範囲はより
広い点で両者はずれている。

列に絞る実装を採らないのは、対応 ID 列の位置・列名が成果物ごとに異なり（`test-analysis.md` は
「対応テストベース」「対応リスク #」の 2 列、`test-case.md` は未作成で列構成が未確定）、
列の特定に成果物ごとの設定が要るため。**この基盤が検出できるのは「ID がどこにも現れない」
完全な欠落までで、「表に無いが散文にはある」中途半端な引き継ぎは検出できない**。判定の
厳密化が必要になったら、`test-case.md` の列構成が確定した時点で列指定方式へ変更する。

### 母数が 0・下流が未作成のときの扱い

**下流成果物が存在しない場合**、その集計はカバー率 0%、未カバー ID 欄に全 ID が並ぶ
（母数は上流から数えるので保たれる。欠落として正しく現れる）。出力冒頭に未作成である旨を
注記する。

**母数が 0 になるのは上流成果物が存在しない場合**で、このときカバー率を `—` と表示する。
上流と下流は集計項目ごとに異なる点に注意する。例えば `test-analysis.md` が未作成のとき、
`REQ / NFR / AC / R# → テスト条件` は下流欠落として 0% になるが、`test-analysis.md` を
上流とする `テスト条件 TC# → ケース` は母数 0 で `—` になる。

  AC 消化率へ畳まず独立した行として残している。
- **test-plan 4 章の完了基準 9 項目すべてに、2 章または 3 章のいずれかのメトリクスが
  対応している**（基準 1・2 は 2 章のトレーサビリティ系がその前提を、3 章の消化率が達成を測る）。

- **カバレッジ（ライン/ブランチ）は本基盤の採用メトリクスに含めない**。既存 `go-coverage` job が

  仕様のスコープ外に「台帳へのカバレッジ列の追加」「カバレッジ閾値ゲート」「カバレッジの
  トレンド・履歴追跡」が明示されており、重複・矛盾を避ける。
- **テスト実行時間は採用しない**。test-plan 3 章のとおり母集団 17 件・テスト一覧 320 行台と
  小規模で、静的走査のみで生成できるため実行時間が問題にならない。

## 4. 計測基盤（実装物）

- 集計スクリプト: `tests/traceability/run.sh`
  - 入力: `docs/dev/<対象>/spec.md` / `docs/test/<対象>/test-plan.md` /
    `test-analysis.md` / `test-case.md`（対象名を引数で受ける）
  - 出力: 標準出力へ markdown の集計表（集計項目・母数・未カバー・カバー率・未カバー ID）
  - 依存: bash + awk + grep のみ。**Nix 評価も Go ビルドも要さない**。docs のみの変更でも
    走らせられるようにするため（既存の nix 実走最適化〔ADR-0027〕とは独立に保つ）
  - 終了コード: 集計できたら 0。**対象の仕様が存在しない場合も「計測対象なし」として 0**
    （機能単位の作業ディレクトリ `docs/dev/<対象>/` は完成後に削除される運用のため、
    撤去のたびに CI が赤くなることを避ける。撤去時は job も併せて削除する旨を出力へ案内する）。
    引数不正（対象名なし・パス区切りを含む対象名）のみ 2。**カバー率による
    非ゼロ終了はしない**
- CI 設定: `.github/workflows/test.yml` の `traceability` job（新設）
  - `changes` ゲートを通さず**常時実行**する。この job は docs 配下の成果物を計測対象とするため、
    nix / Go のパスで判定する既存 `run` 出力でゲートすると、計測したい docs のみの PR が
    そのまま skip される
  - `Setup Nix` を持たない（素の bash で足りる）ため実行コストは数秒
  - 既存 job（`changes` / `flake-check` / `go-coverage` / `e2e`）には一切変更を加えていない
- 可視化: **Job Summary のみ**（`GITHUB_STEP_SUMMARY`）。既存 `go-coverage` と同じ方式。
  README バッジ・PR コメントは採用しない（後者は `pull-requests: write` 権限の追加を要し、
  既存の慣習にも無い）
- **required status check には登録しない**。計測・表示のみでゲートを持たない設計であり、
  カバー率が下がってもマージを止めるべき対象ではないため（既存 `go-coverage` が required
  check に含まれていないのと同じ理由）。なお完成の定義（`definition-of-done.md`）への
  追加も行わないが、これは別の判断である — required status check の登録と完成の定義の
  項目は連動しない機構で、ADR-0030 の required check 4 件に対し完成の定義の `ci-check` は
  2 件のみと 1:1 対応していない

### 動作確認の記録

- `shellcheck tests/traceability/run.sh` — 警告なし
- `actionlint .github/workflows/test.yml` — 警告なし
- 実リポジトリでの実行 — 集計成立（REQ / NFR / AC / R# → テスト条件がいずれも 100%、
  TC# / AC → ケースは `test-case.md` 未作成のため 0%）
- 負例のフィクスチャ（上流 ID の一部を下流から欠落させたもの）で、未カバー ID の列挙と
  カバー率の低下が正しく現れることを確認
- 異常系 — 引数なし・パス区切りを含む対象名で終了コード 2、存在しない対象で終了コード 0
  （「計測対象なし」の案内を出力）、
  スクリプト位置からのリポジトリルート解決が呼び出し時の作業ディレクトリに依存しないこと

## 5. 運用メモ

- 計測は上記基盤が **自動で** 行う。pull_request ごとに Job Summary へ集計表が出る。
- 数値の評価・完了判定は `/test-report quality-observability` で行う。
- `test-case.md` を作成したら、ケース化系の 2 メトリクスが自動で実数を返すようになる
  （スクリプトの変更は不要）。3 章の未実装メトリクスの有効化は別途実装が要る。
- 新しいテスト対象へ流用する場合、`run.sh` は対象名を引数で受けるため、workflow の
  引数を増やすだけで済む（スクリプト自体は対象非依存）。
