# mini テストモニタリング定義: quality-observability

> 詳細は本編 [`test-monitoring.md`](test-monitoring.md) を参照。本書は nput の CI・テスト
> プロセスに詳しくない人向けの要約。

## 1 分で分かるこの基盤

テストの準備は「仕様書に書いた要求 → 起こりうる事故（リスク）→ 何を確認するか（テスト条件）
→ 具体的なテスト手順（ケース）」という順に、4 つのドキュメントへ受け渡しながら進む。
このとき **前の書類に書いた項目が次の書類へ引き継がれず、静かに消える**ことがある。

この基盤は、各ドキュメントに振られた番号（`REQ-01` や `R1` のような ID）を突き合わせて、
**どこかで消えた項目を見つけて一覧に出す**仕組み。PR を出すたびに自動で走り、結果が GitHub の
画面に表示される。数値でマージを止めることはしない（見えるようにするだけ）。

なお **テストそのものの成否や、テスト対象のコードの良し悪しは測っていない**。測っているのは
「テストの計画書類が繋がっているか」だけ。

## 何を測るか

| 測るもの | 一言でいうと | どうなったら黄信号か |
|---|---|---|
| REQ → テスト条件 | 仕様書に書いた機能の要求が、確認項目に引き継がれているか | 100% を下回る |
| NFR → テスト条件 | 同上（速度・静かさなど、機能以外の要求について） | 100% を下回る |
| AC → テスト条件 | 「これができたら完成」の条件が、確認項目に引き継がれているか | 100% を下回る |
| リスク → テスト条件 | 想定した事故が、確認項目に引き継がれているか | 100% を下回る |
| テスト条件 → ケース | 確認項目が、実際のテスト手順に落ちているか | 100% を下回る |
| AC → ケース | 完成条件が、実際のテスト手順に落ちているか | 100% を下回る |

- **下 2 つは現在 0%**。テスト手順書（`test-case.md`）がまだ無いため。書類ができれば自動で
  実数に変わる（設定変更は不要）。
- テスト計画の完了基準との対応は本編のメトリクス定義表を参照。
- 数値が下がっても CI は赤くならない。マージを止める仕組みではない。

## どこで見られるか

- **GitHub の PR → Checks タブ → `traceability` job → Summary**。PR を出すたびに自動で表を出す
  （既存のカバレッジ表示と同じ場所）。
- 手元で見たいときは `tests/traceability/run.sh quality-observability` を実行する。
  Nix も Go も不要で、数秒で終わる。

## 測れていないもの

取得元のデータが存在しないため、次の 3 つは**まだ測っていない**（issue #204 で追跡）。

- **テストの失敗率** — テスト実行の結果が機械で読める形式（JUnit XML 等）で出ていないため
- **flaky（不安定）率** — 同じ条件なのに成功したり失敗したりするテストの割合。上と同じ理由
- **CI が正しく動いたかの観測** — 測る対象の CI 設定自体がまだ実装されていないため

## やらないこと

- **数値の解釈・傾向分析はこの基盤ではしない**（「なぜ下がったか」の評価は `/test-report` の担当）。
- **AI が継続的に数値を見張ることもしない**。計測は CI が自動で行う。
