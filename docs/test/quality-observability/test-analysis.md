- 複数のテスト条件へ跨る受け入れ条件がある（AC-01 → TC-04・TC-05、AC-05 → TC-04・TC-05）。
  対応関係の正本は表の「対応テストベース」列とする。
- 表の「対応テストベース」「対応リスク #」列は ID を**個別に列挙**する（`AC-07〜AC-10` の
  ような範囲表記を使わない）。トレーサビリティ集計が ID の突き合わせで行われ、範囲表記からは
  **両端の ID だけが「参照あり」と判定されて中間の ID が未カバーとして残る**ため、
  カバー率が実態より高く出る（欠落を部分的に隠す偽陽性になる）。本文中の説明での範囲表記は
  許容する。詳細は `test-monitoring.md` 2 章「ID 表記の規約」を参照。
- 受け入れ条件（AC）に現れない機能要求も条件化している。TC-06（REQ-01 の表構造）と
  TC-14 の限界明記（REQ-03）は対応する AC を持たないため、AC 側からの突合では検出されない。
  AC の網羅だけを完了判定に使うと、これらの要求が未実装のまま全 AC が充足しうる。
- TC-11 は**生成モードに限定**する。NFR-02・AC-04・R8 の 3 つがそろって生成を対象としており、
  検証モードの Nix 非依存を要求する記述は仕様に無いため（原則どおり定義の外延を広げない）。
  なお REQ-07 により検証は内部で台帳を再生成するため、生成が静的走査のみで完結すれば検証も
  派生的に同じ性質を持つ。この派生関係は仕様が明示していないので、条件としては立てない。
- TC-07 の「非ゼロ終了・標準エラー出力」と TC-12 の「標準出力の沈黙」は、判定手段ではなく
  要求そのものとして残している（REQ-06 が失敗時の標準エラー出力への列挙を、NFR-01 が成功時の
  標準出力の沈黙を、それぞれ振る舞いとして規定しているため）。どの値・どの文言が出るかの
  具体化は test-design が担う。
- 粒度: 機能領域ごとに 1 条件へ畳んでいる。test-plan 3 章 (a) の変更パターン ①〜④、
  REQ-02 の数え方の区分、検証の 4 失敗パターン、および各条件の具体的な期待値は、条件の内側に
  束ねてケース導出（test-design）の素材として引き継ぐ。

## 3. 優先度の根拠

- **高（TC-01・TC-02・TC-03）** — test-plan の高リスク R1（検証 check の skip による腐敗の
  素通り）・R4（非決定性による恒常的失敗）に直接対応する。R1 は「skip が required status
  check 上は成功扱い」という性質上、誤配線が静かに成立して観測されない点が影響度を押し上げて
  いる。TC-01 と TC-02 は R1 の別々の失敗モード（実行されない／実行されるがマージを止めない）
  に対応するため、独立した条件として分離した。
  - **TC-01 は R1 と R2 を同一の観測で兼ねる**。両者は同じ変更パターンの PR で同時に
    観測できる（検証 check が実行されるか／既存の nix job が誘発されないか）ため、条件を
    分けると同一の実行を二重に数えることになる。ただし R2 は中リスクであり、
    **test-plan 完了基準 1（高リスク R1・R4 の消化率）の分母には R1 相当のケースのみを
    計上する**。R2 相当のケース（既存 job の非誘発）は分母に含めない。
- **中（TC-04〜TC-10）** — リスク由来の条件（R3: TC-04・TC-05 / R5: TC-05 / R6: TC-10）と、
  リスク非対応でツールの中核機能として条件化したもの（TC-06・TC-07・TC-08・TC-09）が
  混在する。いずれも通常の実装バグとして現れ、判定点が明確で検出も容易。
  - **リスク紐づけの原則**: 対応リスク欄には、test-plan の R1〜R8 の**定義文に一致する
    ものだけ**を書く。近接する内容であっても定義の外延を広げて当てはめない（リスク別の
    消化率が実態とずれるため）。定義に一致するリスクが無い条件は `—` とし、仕様の中核
    機能として条件化する。
  - **R3 の担い手は TC-04 と TC-05**。R3 は「抽出母集団の**件数**が実装の規則逸脱により
    台帳と食い違う」ことに限定されたリスクで、TC-04 が抽出器側の規則適合を、TC-05 が
    その帰結（台帳が母集団を過不足なく反映しているか。AC-01 の件数一致）を担う。
    TC-05 は R3・R5 の両方に対応するが、両者は条件の別々の部分に対応する（前半＝母集団の
    反映が R3、後半のうち**「仕様参照」列**の欠落表現が R5）。「テスト所在」列の `なし` は
    REQ-03 の命名規約由来で R5 の射程外。両リスクは完了基準・モニタリングのいずれの分母にも
    なっていないため、消化率の分母には双方へ計上してよい。
  - **TC-06〜TC-09 の対応リスクは `—`**。表構造・腐敗の検出・非破壊性・`apps.qa-tracer` の
    起動は、R1〜R8 のいずれの定義にも該当しない。特に TC-06（列構成）は、列の誤りが母集団
    件数の食い違いを生まないため R3 に該当しない。
  - **リスク評価側の空白**: TC-07（検証モードが腐敗を検出できない）は、R1 と同一の帰結
    （腐敗の素通り）を別経路でもたらすが、R1〜R8 に検証ロジック自体の欠陥へ対応する
    リスク項目は無い。これは test-plan のリスク評価の網羅上の空白であり、本分析では
    中核機能として条件化して埋めている（リスク項目の追加は test-plan の領分）。
- **低（TC-11〜TC-14）** — 低リスク R7・R8、および退行余地の小さい静的確認。現状 root / dev
  いずれの flake にも `apps` 出力が無く、`docs/design.md` にも `docs/quality/` の言及が無い
  （いずれも実物で確認済み）ため、初回実装で満たされたか否かの単純判定で足りる。

## 4. カバレッジの見立て

- **網羅する観点**: 公開契約 3 系統の抽出規則、台帳の生成内容・表構造・網羅性、検証の
  4 失敗パターンと非破壊性、CI ゲートの実行制御とマージブロック、決定論性、沈黙、
  公開面の非汚染、ドキュメント追従。
- **要求側からの網羅**: REQ-01〜REQ-10・NFR-01〜NFR-05 のすべてがいずれかのテスト条件に
  対応している。受け入れ条件 AC-01〜AC-19 の 19 件も同様（対応関係は 2 章の表が正本）。
- **意図的に除外した観点**:
  - 性能・セキュリティ・ユーザビリティ（開発者専用の内部ツールで、母集団 17 件・一覧 320 行台と
    小規模。test-plan 3 章の判断を踏襲）
  - テスト一覧の鮮度（1 章のとおり仕様上の検証対象外）
  - テスト内容の妥当性判定（REQ-03 の明示的限界。限界の明記自体は TC-14 で扱う）
- **既存テストによるカバー**: なし。`qa-tracer` / `traceability` / `docs/quality` は実装・
  テストとも未着手であることを確認済みで、重複回避の対象は存在しない。
- **テスタビリティ上の制約**:
  - TC-01・TC-02 は実 PR 上でしか観測できず、TC-02 は ruleset 登録にリポジトリ管理権限を要する。
  - TC-03 の「列挙順の撹乱」は実装言語の決定（基本設計）に依存し、撹乱手段はケース設計時に
    確定する。
  - TC-05 の「仕様参照」列は、`docs/spec.md` の見出し構成上 lib 系統でしか見出し解決が
    成立しない（CLI 6 件は `### サブコマンド体系` のコードブロック内、モジュールオプション
    5 件は `### 共通オプション（全モジュール）` に集約、lib も 3 API が 1 見出しを共有）。
    REQ-05 の見出し実在検証が実質 lib 系統にしか効かないことは R5 のとおり織り込み済みで、
    `なし` の多発は仕様どおりの正しい観測結果として扱う。
