## 補足

- **完了基準 1（高リスク R1・R4 の消化率）の分母**: R1 に紐づくケースは CASE-01・CASE-04・
  CASE-07・CASE-10・CASE-13・CASE-14・CASE-15・CASE-16 の 8 件、R4 に紐づくケースは
  CASE-17・CASE-18・CASE-19・CASE-20 の 4 件で、合計 12 件。`test-analysis.md` 3 章のとおり
  **R2 相当のケース（既存 job の非誘発。CASE-02・CASE-03・CASE-05・CASE-06・CASE-08・
  CASE-09・CASE-11・CASE-12 の 8 件）は分母に含めない**。
  - **この分母は可変**である。**CASE-19 が実装言語の決定により不要と判断された場合
    （下記「CASE-19 の適用条件」）は分母から除外し、R4 の分母を 3 件・合計を 11 件とする**。
    その判断と根拠は test-implement が記録する。除外せずに未実行のまま残すと、正当な除外で
    あるにもかかわらず消化率が 12 分の 11 となり、完了基準 1（消化率 100%）と
    `test-monitoring.md` 3 章「高リスク項目のケース消化率」が機械的には未達に見える。
- **ケース間の前提依存**: CASE-14 は CASE-13 の pass を、CASE-16 は CASE-15 の pass を
  それぞれ前提とする（check の報告状態が期待どおりでなければ、マージ可否の判定が意味を
  持たないため）。CASE-13・CASE-15 はいずれも CASE-01 の pass を前提とする（台帳のみの変更で
  check が実行されなければ、台帳の状態が check の結果へ反映されるかを観測できない）。
  CASE-18・CASE-20 は CASE-17 の出力を比較対象に使う（CASE-19 は 3 回以上の自己実行内で
  比較するため CASE-17 に依存しない）。**ケース間の依存はすべて前提条件欄に記載する**
  （補足だけに書かない）。
- **CASE-15 が CASE-41 の pass を前提とする理由**: CASE-15 の判定点は CI 配線（R1）だが、
  台帳の壊し方に「母集団に無い行を追加」を選んでいるため、検出そのものは REQ-06 の過剰側
  （AC-09 / CASE-41）の実装に依存する。**検証ロジック側の欠陥で CASE-41 が落ちると
  CASE-15 も連鎖して失敗し、CI 配線の欠陥か検証ロジックの欠陥かを切り分けられない**。
  CASE-41 を先に通しておくことで、CASE-15 の失敗を CI 配線の問題として解釈できる。
- **TC-02 の健全側ケース（CASE-13・CASE-14）の位置づけ**: 腐敗側（CASE-15・CASE-16）だけでは
  「常に failure を返す check」が全件を通過してしまう。健全側は test-plan 完了基準 8 が重大
  欠陥として名指しする「偽陽性で正常な PR が赤になる」状態の検出点として置いている。
- **CASE-19 の適用条件**: 実装言語が連想配列の反復順を保証する場合（Nix の attrset は評価時に
  属性名の辞書順へ正規化される）は、この要因による非決定性が原理的に生じないため、実装言語の
  決定後に test-implement が本ケースの要否を判断する。
- **CASE-21・CASE-23・CASE-28・CASE-52 の件数**: 括弧内の数値は本ケース作成時点（2026-07-27）の
  スナップショットで、判定は母集団との一致で行う（件数をハードコードしない）。公開契約も
  テストも未完了 epic の消化に伴って増えるため、これらの件数は正常に変動する。仕様の
  「件数表記の扱い」節および test-plan 5 章に対応する。
- **CASE-37・CASE-38 の対応 AC が `—` である理由**: REQ-05 は失敗契機を 2 つ規定するが
  （テスト所在のパス不在・仕様参照の見出し不在）、受け入れ条件は前者（AC-07）にしか対応する
  項目を持たない。後者は AC からの突合では検出されない要求のため、リスク R5 を対応欄に置く。
- **TC-05 のリスク射程の違い**: CASE-29（「仕様参照」列）は R5 を持つが、CASE-30・CASE-31
  （「テスト所在」列）は AC のみを持つ。`test-analysis.md` 4 章のとおり、「テスト所在」列の
  `なし` は REQ-03 の命名規約に由来し、R5（「仕様参照」列の解決不能）の射程外であるため。
- **CASE-61 と CASE-62 の分割**: `docs/quality/README.md` の検査のうち、ファイルの存在と
  限界を示す記述の有無は文字列一致で機械判定できるが（CASE-61）、「読み方と目的が伝わるか」は
  意味判断のため人の確認が要る（CASE-62）。
- **CASE-57 の対応 AC が `—` である理由**: TC-13 は AC-13（flake outputs / CLI）と NFR-05
  （`lib/` の依存）の 2 系統を束ねており、本ケースは後者に対応する（→ `test-design.md` 1 章）。
- 対応 ID は個別に列挙している（範囲表記・スラッシュ併記を使わない）。トレーサビリティ集計が
  ID の文字列突き合わせで行われるため。詳細は `test-monitoring.md` 2 章「ID 表記の規約」
  および「上流の ID 省略記法」を参照。
