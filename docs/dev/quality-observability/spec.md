# quality-observability 仕様

作成日: 2026-07-26

## 目的

nput は公開契約（CLI サブコマンド 6 件 + lib 公開 API 6 件 + モジュールオプション 5 件）・
実装・テスト（Go テスト関数 254 件 / nix-unit 40 件超 / namaka スナップショット / e2e 7 シナリオ）・ドキュメント
（`concept.md` / `design.md` / `spec.md` の計 2147 行 + ADR 47 本）を抱え、これらの対応関係を
人が把握できない規模に達している。未完了 epic が 7 件控えており規模はさらに増える。

現状「ドキュメントが実装に追従しているか」は `docs/dev/definition-of-done.md` の DOD-04 で
人判定に置かれており、人力で吸収しきれていない。本機能は **公開契約・仕様記述・テストの
対応関係を機械的に観測可能にし、対応関係の欠落を CI が検出する状態** を作る。

カバレッジ率という単一指標ではなく「何が存在し、何に対応し、何が欠けているか」の全体像を
得ることが目的であり、テストの十分性を判定することは目的としない。

## スコープ

- **観測対象**: nput の公開契約 3 種
  - CLI サブコマンド（`cmd/nput/*.go` の cobra `Use:` 宣言）
  - lib 公開 API（`lib/default.nix` が公開する属性）
  - モジュールオプション（`modules/*.nix` の `mkOption` / `mkEnableOption`）
- **成果物の配置**: `docs/quality/` 配下（恒久資産。機能単位の作業ディレクトリではない）
- **生成・検証の実行主体**: `dev/flake.nix` の `apps.qa-tracer`
- **検証の実行契機**: GitHub Actions の pull_request
- **利用者**: 本リポジトリの開発者（nput の外部利用者へは公開しない）

## 機能要求

### REQ-01: 公開契約の台帳を生成する

- `docs/quality/traceability.md` に、公開契約 1 件を 1 行とする表を出力する。
- 表の列は「機能」「仕様参照」「テスト所在」の 3 列とし、カバレッジ率の列を持たない。
- 「機能」列は公開契約の識別子（例: `apply` / `mkManifest` / `nput.entries`）と種別
  （CLI / lib / module）を含む。
- 「仕様参照」列は `docs/spec.md` 内の該当見出しへの参照を書く。該当記述が存在しない場合は
  `なし` と明示する（空欄にしない）。
- 「テスト所在」列は当該機能に対応するテストファイルのリポジトリ相対パスを書く。存在しない
  場合は `なし` と明示する。

### REQ-02: 公開契約の母集団を機械抽出する

- CLI サブコマンドを `cmd/nput/*.go` の cobra `Use:` フィールドから抽出する。root コマンド
  （`Use: "nput"`）は台帳の行に含めない。
- lib 公開 API を `lib/default.nix` が公開する属性から抽出する。`__internal` は公開 API では
  ないため台帳の行に含めない。
- モジュールオプションを `modules/*.nix` の `mkOption` / `mkEnableOption` 呼び出しから抽出する。
  数え方は次の規則で確定する:
  - オプションの**宣言**だけを数える。`inherit (lib) mkOption` のような関数の取り込み行は
    宣言ではないため含めない。
  - submodule 型の親オプションと入れ子の葉オプションはそれぞれ 1 件と数える
    （`nput.backup` / `nput.backup.enable` / `nput.backup.suffix` は 3 件）。
  - `modules/flake-parts.nix` が `mkTransposedPerSystemModule` で宣言する transposed
    オプション（`perSystem.nput`）は flake-parts の配線であり、モジュール利用者へ公開する
    オプションではないため母集団に含めない。
- 抽出は静的解析（ソースの走査）で行い、Nix の評価（`nix eval`）を必要としない。

### REQ-03: テストの所在を命名規約で紐づける

- CLI サブコマンド `<name>` に対し `cmd/nput/<name>_test.go` の存在を確認し、存在すれば
  テスト所在として記録する。
- lib 公開 API およびモジュールオプションに対し、`tests/nix-unit/*.nix` および
  `tests/namaka/` 配下の対応するテストを記録する。
- 紐づけは「テストの所在」を示すものであり、当該テストがその機能を検証していることを
  保証しない。この限界を `docs/quality/README.md` に明記する。

### REQ-04: テスト一覧を出力する

- Go テスト関数・nix-unit テスト・namaka スナップショットテスト・e2e シナリオを人が
  俯瞰できる一覧として出力する。
- 一覧は少なくとも「テスト名」「所在ファイル」「種別（Go / nix-unit / namaka / e2e）」を含む。
- 出力形式（markdown / HTML / その他）は本仕様では規定せず、基本設計で決定する。

### REQ-05: 台帳の参照生存を検証する

- 台帳の「テスト所在」列に記載されたパスが実在しない場合、検証を失敗させる。
- 台帳の「仕様参照」列が指す `docs/spec.md` の見出しが実在しない場合、検証を失敗させる。
- `なし` と記載された欄は検証対象外とし、失敗させない。

### REQ-06: 台帳の網羅性を検証する

- REQ-02 で抽出した母集団に存在し、台帳に行が無い機能がある場合、検証を失敗させる。
- 台帳に行が存在し、母集団に存在しない機能がある場合、検証を失敗させる。
- 失敗時は、どの機能が過不足しているかを標準エラー出力に列挙する。

### REQ-07: 生成物とコミット内容の一致を検証する

- 検証時に台帳を再生成し、リポジトリにコミットされた `docs/quality/traceability.md` と
  内容が一致しない場合、検証を失敗させる。
- 失敗時は差分を標準エラー出力へ表示する。
- 検証は台帳ファイルを書き換えない（検証と生成を別の動作として分離する）。

### REQ-08: `apps.qa-tracer` として起動できる

- `dev/flake.nix` の `perSystem` に `apps.qa-tracer` を定義し、
  `nix run '.?dir=dev#qa-tracer'` で起動できる。
- 生成モードと検証モードを持ち、引数で切り替える。
- root の `flake.nix` には `apps` 出力を追加しない。
- `nput` バイナリのサブコマンドとして実装しない。

### REQ-09: CI で検証し、マージを止める

- GitHub Actions の pull_request で REQ-05 / REQ-06 / REQ-07 の検証を実行する。
- 検証を required status check として `main branch protection` ruleset に登録し、失敗時に
  main へのマージを不可能にする。
- `.github/actions/changes` へ第 2 出力 `quality` を追加し（検出対象: `**.nix` / `**.go` /
  `docs/quality/**` / `docs/spec.md`）、検証 job はこの出力でゲートする。既存の `relevant`
  出力は変更しない（docs のみの変更で `flake-check` / `e2e` / `go-coverage` の nix 実走を
  避ける最適化〔ADR-0027〕を維持するため）。これにより台帳のみを変更した pull_request でも
  検証が実行される。`docs/spec.md` を検出対象に含めるのは、REQ-05 の見出し実在検証が
  `docs/spec.md` の見出し文字列に依存し、見出しの改名で検証が壊れるためである。

### REQ-10: 完成の定義へ機械判定項目を追加する

- `docs/dev/definition-of-done.md` の機械判定テーブルへ DOD-05 として本検証を追加する。
- 種別 `ci-check`、対象は GitHub Actions の check 名、条件 `success` とする。
- 追加により機械判定・人判定の合計が上限 5 件に到達し、以後の項目追加には既存項目の統合
  または除外が必要になることを同ファイルに明記する。

## 非機能要求

- **NFR-01**: 検証成功時の標準出力は空とする（ADR-0031「成功時は沈黙」に準拠）。失敗時のみ
  標準エラー出力へ理由を出す。
- **NFR-02**: 台帳の生成は Nix の評価を必要とせず、リポジトリの作業ツリーの静的走査のみで
  完結する（REQ-02 に対応）。
- **NFR-03**: 台帳の生成は決定論的であり、同一の作業ツリーに対し常に同一の出力を返す
  （REQ-07 の差分検証が成立する前提）。
- **NFR-04**: `docs/design.md` の「テスト戦略」節へ本観測基盤の記述を追加し、DOD-04（設計
  ドキュメントの実装追従）に抵触しない状態にする。
- **NFR-05**: 本機能の追加は `lib/` の依存関係を変更しない（`lib/` は nixpkgs のみに依存する
  という既存規約を維持する）。

## スコープ外

- **カバレッジ閾値ゲート**（既存 ADR の「閾値ゲートを持たない」設計を維持する。マージ順依存を
  避けるため）
- **カバレッジのトレンド・履歴追跡**（目的は全体像の把握であり、履歴を蓄積しても取る行動が
  変わらないため）
- **`docs/spec.md` の全面 ID 化（`REQ-#` 付与）**（別 epic issue として起票し、本機能の台帳
  出力を見てから着手する）
- **`internal/*` パッケージの台帳掲載**（公開契約ではなくリファクタが自由であるべき領域。Go
  カバレッジで既に観測できている）
- **既存 254 件のテストへの仕様 ID アノテーション付与**（付与コストが大きく、付け忘れを機械が
  検出できないため）
- **台帳へのカバレッジ列の追加**（カバレッジはパッケージ単位、台帳は機能単位で粒度が一致せず、
  Nix 側にはカバレッジの概念が存在しないため）
- **docs サイト（issue #57）への統合**（#57 は優先度の低い未着手 epic であり、依存すると本機能が
  着手できなくなるため）
- **`nput` バイナリへのサブコマンド追加**（配布物の公開契約を開発専用ツールで汚染しないため）
- **root `flake.nix` への `apps` 出力追加**（外部利用者の flake outputs に開発ツールを露出させ
  ないため）
- **ドキュメントの整理・実装との乖離修正そのもの**（本機能の台帳出力を見てから対象を決める
  後続作業。別 epic issue として起票する）
- **台帳の自動コミット（bot による更新）**（main の ruleset と相反し、腐敗が自動修復されると
  人への通知にならないため）
- **テストが機能を実際に検証しているかの判定**（機械が保証するのは対応関係の欠落が無いことで
  あり、対応関係の内容の正しさではない）
- **ADR 47 本の有効性・置換関係の判定**（機械判定の手段が無いため）
