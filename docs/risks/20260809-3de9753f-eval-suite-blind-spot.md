# RISK-3de9753f: GC アンカーの取り違えと評価スイート自身の盲点で検証が空洞化する

## リスク

2 つの破れを 1 つの脅威として束ねる。どちらも「評価層の検証が通っているのに守られていない」
という同じ形をとる。

**GC アンカーの取り違え**: symlink farm は GC アンカー専用で、アンカーは store-backed な
symlink entry に限る（REQ-b12fc3c0）。アンカー名は target のハッシュ（REQ-62eda895）で、
farm derivation は `mkManifest` の返り値に含まれる（REQ-60e6b49c）。抽出条件が緩めば copy や
out-of-store の entry までアンカーを持ち、逆に厳しすぎれば store-backed な symlink が
アンカーを失う。後者は世代が積まれた後（REQ-1be4d678）に前世代の store パスが GC で回収され、
ロールバック先が壊れるという形で現れる。アンカー名が非決定的になれば、同じ target が世代
ごとに別名のアンカーを持ち、間引きの対象を特定できなくなる。

**評価スイート自身の盲点**: 検証手段を nix-unit（点の不変条件）と namaka（面のスナップ
ショット）の 2 本立てにする設計（DSG-fb49e36c）に固有の破れが 2 つある。nix-unit のスイートは
ディレクトリ列挙で組み立てられ `//` マージが後勝ちで衝突を黙って解決するため、テスト名が
ファイル横断で衝突すると、落ちるはずのアサートが実行されないまま緑になる。namaka のスナップ
ショットは変更時に丸ごと再承認されるため、規範である性質をスナップショットだけに委ねると
「変わったこと」は見えても「変わってよかったのか」は問われない。

**この破れが design に張る理由**: どちらも 2 手段併用という検証設計の選択に由来し、別の設計
（例: 生成した文書を Go 側の契約テストで直接検証する）へ置き換えれば消える。

## 評価

- likelihood: medium — アンカー抽出条件は method × srcKind の組み合わせで分岐し、テスト名の
  衝突はファイル追加のたびに起こりうる
- impact: high — GC アンカーの欠落は前世代の store パス回収 = ロールバック不能を招き、
  スイートの盲点は他の全アサートの信頼性を下げる
- level: high

## 対処

TC-1d69350e（アンカー対象の抽出とアンカー名の決定性）・TC-de6514e2（文書全体のスナップ
ショット回帰とその適用範囲）で緩和する。テスト名のファイル横断一意はスイートの組み立て
規約そのもの（TP-36e90d5d）で、個々の CASE がその制約下にあることを本文へ明記する。
