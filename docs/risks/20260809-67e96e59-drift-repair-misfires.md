# RISK-67e96e59: 世代スキップと lstat ドリフト修復が誤発火し、世代が無限増殖するかユーザーの編集を潰す

## リスク

project mode では、新しい link farm derivation が前世代と同一なら新世代を積まず、
代わりに各 entry の target を `lstat` で検査して記録どおりでないものだけ再張りする
（→ REQ-46fccb80）。この判定が誤ると、方向によって別々の被害が出る。

**スキップすべき場面で積む** — devShell / direnv 運用では `shellHook` がシェル再入の
たびに走る。derivation 同一でも毎回新世代を積めば、世代がシェルを開くたびに増え続け、
`nix-env` の世代一覧も store の gcroot も無限に膨らむ。判定が home mode まで及んで
「適用のたびに新世代」を壊すのも逆向きの誤りで、home mode の rollback 先が失われる。

**修復すべき場面で修復しない** — 「derivation 同一 ⇒ FS 同一」は foreign tool の書き換えで
崩れる。消された symlink・別物に張り替えられた symlink を放置すれば、config が有効な
はずの環境で設定が効かない状態が黙って続く。foreign な実体を再張りしたときに warning を
出さないのも、ユーザーが他ツールとの競合に気付けなくなる形で同じ欠陥に属する。

**修復すべきでないものを修復する** — copy entry のドリフト修復は place-once の意味論を
守る必要がある。target が不在のときだけ再マテリアライズし、存在するが内容が異なる
（＝ユーザーが編集した）場合は触ってはならない。ここを取り違えると、ユーザーがローカルで
編集した設定ファイルがシェル再入のたびに黙って上書きされる。`--recopy` を明示したときは
逆に上書きするのが正しい。

## 実現性

**likelihood: high** — 発火頻度が極めて高い経路（シェル再入のたび）で、判定の入力が
derivation の同一性と FS の実測という 2 系統に分かれている。

**impact: high** — どの方向の誤りも沈黙の不整合として現れる。copy entry の編集はシェル
再入のたびに黙って上書きされ（copy は世代管理外なのでロールバックでも戻せない）、修復し
損ねた symlink は設定が効かない状態を黙って続ける。世代の無限増殖も含め、ユーザーの日常
操作の中で静かに進行し、気づく契機が無い。

## 緩和

TC-765858b6（ドリフト修復の対象範囲）と TC-1ee7a729（世代スキップの発火条件と
コミット方針）が緩和する。
